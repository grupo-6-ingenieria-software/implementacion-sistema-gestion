Base local sincronizada con Turso Cloud

Dejar de operar con un archivo SQLite aislado: cada equipo conserva una base local, acepta operaciones sin red y comparte cambios con una base central de Turso.

Proyecto: Sistema Gestión HuáscarEstado: plan, sin implementaciónPrioridad: integridad de ventas y stock

Resumen y alcance

El código actual abre file:./local.db, activa WAL y aplica migraciones/triggers, pero no configura una réplica ni sincroniza con Turso Cloud. El documento técnico ya promete escritura local y sincronización cada cinco segundos.

Resultado esperado

Una venta confirmada queda durable en el equipo; cuando hay red, llega a Turso y luego a las otras cajas, con estado visible y verificación de convergencia.

Condición de seguridad

No habilitar cuatro escritores offline hasta probar claves globales, transacciones, triggers y resolución de conflictos. Un WAL local por sí solo no hace replicación.

Brecha del diseño actual. Hay claves INTEGER AUTOINCREMENT que pueden colisionar entre equipos, y triggers que rechazan ventas sin stock aunque el documento técnico promete aceptarlas y registrar discrepancias. Ambas decisiones deben resolverse antes de sincronizar escrituras.

Evidencia: src/db/client.ts, src/db/schema.ts, src/db/triggers.sql, dimension_tecnica.md.

La aplicación escribe primero en su archivo local. Un coordinador en el proceso principal envía cambios con push(), recibe los de otros equipos con pull() y registra el último éxito y los errores. El renderer consulta el estado por IPC y recarga datos cuando cambie la réplica. La sincronización se programa cada cinco segundos según el requisito, con un ciclo sin solapamientos y reintento con espera progresiva cuando no haya red.

La recomendación actual de Turso para escritura local es Turso Sync (@tursodatabase/sync). Su push() transmite cambios lógicos; no se debe implementar una copia manual del archivo -wal. La elección queda condicionada a la prueba de compatibilidad de la fase 0.

Versiones que requieren prueba. El proyecto usa Drizzle 0.45.2. El driver drizzle-orm/tursodatabase-sync aparece en Drizzle 1.0.0-rc.4; su implementación de transacciones usa una API que el SDK Sync 0.7.2 marca como obsoleta por posible intercalación de sentencias. Además, la documentación de bootstrapIfEmpty:false no coincide con el comportamiento publicado en Sync 0.7.2. El plan no presupone transacciones seguras ni primer arranque offline hasta demostrarlo.
Límite de consistencia. Sin conexión, ningún equipo conoce inmediatamente las ventas de los demás. Las reglas que exigen unicidad global o lectura del stock más reciente necesitan una política de conflicto explícita, incluso si las escrituras locales funcionan.

0 Descubrimiento y prueba vertical Bloquea el resto

Implementar. Crear una prueba desechable con dos bases locales y una base Turso de ensayo: una tabla representativa, una venta con lectura y escritura dentro de transacción, desconexión, push(), pull() y conflicto. Probar el driver de Drizzle compatible con Turso Sync y el empaquetado de su módulo nativo en Electron/Windows. Registrar la versión exacta que funciona y las diferencias de tipos/SQL. Confirmar cómo se migra una base libSQL existente y si una instalación nueva puede iniciarse sin red.

API permitida para el prototipo. Copiar la forma documentada connect({ path, url, authToken }); usar db.push(), db.pull(), db.checkpoint() y db.stats(). Verificar en el paquete instalado si existe bootstrapIfEmpty antes de usarlo: Sync 0.7.2 no lo expone ni lo aplica aunque aparece en la guía. Para Drizzle 1.0.0-rc.4, comprobar drizzle({client: await connect(...), schema}) desde drizzle-orm/tursodatabase-sync y probar aislamiento concurrente; la API nativa transactionAsync(fn) es candidata para flujos críticos si el driver aún usa transaction(). En @libsql/client comparar createClient({url, syncUrl, authToken, syncInterval: 5, offline:true}) y client.sync(); el intervalo legado está expresado en segundos.

Evitar. Interpretar PRAGMA journal_mode=WAL como subida a la nube; usar la base de producción para esta prueba; inventar métodos de Drizzle o parámetros del SDK; dar por seguro el primer arranque offline a partir de una opción que la versión instalada ignora.

Patrones: guía oficial de Sync, guía de réplica embebida, releases de Drizzle, artefacto Sync 0.7.2; código actual en client.ts y sale-service.ts.

3 Coordinador de sincronización

Implementar. Añadir un coordinador único en main. En un ciclo secuencial: comprobar que no haya otro ciclo, enviar cambios pendientes, recibir remotos, registrar la revisión y emitir evento si la base cambió. Programar cinco segundos cuando haya conexión; ante fallo, registrar error y reintentar con espera progresiva y límite. Ofrecer sincronización manual. Ejecutar checkpoint() bajo una política que limite el crecimiento de WAL y medirlo con stats(). No bloquear una venta local por un fallo de red si la fase 0 confirmó durabilidad local.

Modelar el estado como al día, cambios pendientes, sin conexión, sincronizando y error que requiere atención. “Al día” solo cuando el último push() y pull() terminaron y no hay escrituras pendientes conocidas. Dar prioridad a reintentos y registrar fallos persistentes sin exponer credenciales.

Evitar. Silenciar errores de push()/pull(), marcar “sincronizado” por un temporizador solamente, o hacer checkpoint sin seguir el contrato del SDK.

Fuentes: push, pull y stats, checkpoint; eventos actuales en dashboard-events.ts.

4 Migración de datos y despliegue gradual Riesgo alto

Implementar. Preparar una base Turso de ensayo del motor Turso (no asumir que una instancia libSQL Cloud existente sirve como destino de Sync) y una copia íntegra de local.db. Confirmar el tipo de base remota; para una nueva, Turso documenta turso db create NOMBRE --tursodb y URL turso://.... Exportar e importar con herramientas soportadas; validar conteos, hashes de tablas críticas, FKs, triggers y saldo de caja/stock. No conectar directamente un archivo libSQL existente como réplica nueva sin comprobar conversión y bootstrap del SDK. Definir una ventana de corte: detener escrituras antiguas, capturar respaldo, importar base central, verificar, instalar un solo equipo, probar, luego incorporar los demás con identidad local independiente.

Planificar una reversión operativa: conservar copias previas y una vía de operación controlada si falla la sincronización, sin mezclar escrituras nuevas con la versión anterior. Los scripts de migración deben ser repetibles en ensayo, registrar su versión y rechazar doble importación. El paso a producción requiere credenciales y base Cloud aprovisionadas por el responsable; el plan no incluye editar archivos de entorno.

Evitar. Abrir el archivo de la réplica desde otra herramienta mientras sincroniza, reutilizar o clonar el mismo archivo en dos equipos, restaurar una copia antigua y seguir sincronizando sin procedimiento validado, publicar credenciales o activar escrituras simultáneas antes de pasar las pruebas de conflicto.

Archivos: init.ts, seed.ts, apply-triggers.ts. Referencias: bootstrap de Turso Sync, creación de base, migración Cloud, riesgo de restauración de cliente Sync.

Criterios de salida del proyecto

  1. Una operación crítica se guarda localmente y permanece después de cerrar y reabrir la aplicación sin red.
  2. Al reconectar, cada operación aceptada llega exactamente una vez al conjunto de datos lógico de Turso y aparece en otro equipo.
  3. Las colisiones de claves y conflictos concurrentes siguen una política comprobada; no desaparecen ventas ni auditorías.
  4. El estado mostrado coincide con el resultado real de push/pull y permite diagnosticar retrasos.
  5. La migración, el respaldo y la recuperación han sido ensayados con datos representativos antes del despliegue gradual.
Dependencias externas. Para la integración final se necesitan una base Turso Cloud de ensayo y otra de producción, URLs y tokens aprovisionados por el responsable. El repositorio no contiene esas credenciales y este plan no las crea.
