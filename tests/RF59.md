# RF59 Restablecimiento de contraseña

El RF59 y CU59 permiten al Dueño restablecer la contraseña de un usuario desde
Gestión de usuarios. El criterio CP63 del informe de planificación exige una
clave temporal de ocho caracteres, mostrada una sola vez, almacenada como hash,
con vigencia de 24 horas, cambio obligatorio después del login y rechazo de las
sesiones anteriores incluso cuando sus JWT todavía no han expirado.

## Implementación

- V03 invoca `auth:restablecer-password` (C02), confirma la operación y bloquea
  solicitudes repetidas mientras se procesa o se muestra la clave. El diálogo
  informa la vigencia de 24 horas; al cerrarlo, actualizar la lista o recargar la
  aplicación no permite recuperar la clave. Los errores permiten reintentar.
- C02 autoriza al Dueño con la identidad autenticada y el rol efectivo de la
  sesión. Genera ocho caracteres alfanuméricos mediante `crypto.randomInt`,
  guarda un hash bcrypt y la expiración, cierra todas las sesiones abiertas del
  usuario objetivo con motivo `sistema` y registra la auditoría del solicitante
  con `UsuarioVersion`. Todo ocurre en una transacción: un fallo revierte la
  contraseña, la revocación y la auditoría. La clave en texto se devuelve solo
  en la respuesta del restablecimiento y no se guarda en la base ni en el log.
- El canal heredado `usuario:solicitar-restablecimiento` reutiliza el mismo
  servicio y transmite el rol efectivo de la sesión.
- C01 usa únicamente la última contraseña registrada y rechaza temporales
  vencidas, sin expiración o con una fecha inválida. La clave vence exactamente
  al cumplirse las 24 horas. El orden de inserción desempata registros creados
  en el mismo milisegundo.
- V01 redirige el login temporal a V02. Main permite a su JWT solamente
  `auth:cambiar-password`, `auth:verificar-sesion` y `auth:logout`; también
  rechaza los accesos directos a canales de negocio y audita su denegación.
- C05 consulta el estado persistido de la sesión en cada solicitud protegida.
  Las sesiones revocadas se rechazan aunque el JWT conserve una firma y
  expiración válidas; el heartbeat existente devuelve la interfaz al login.
- El cambio a definitiva comprueba complejidad, diferencia respecto de la
  temporal y vigencia. Guarda el hash, cierra las sesiones temporales y audita
  en una transacción. V02 limpia su token y muestra la confirmación en V01,
  donde el usuario inicia sesión con la definitiva para obtener un JWT nuevo.
  El borrador de venta conserva su mecanismo de recuperación tras ese login.

No se requieren cambios de esquema ni migraciones.

## Pruebas

`tests/main/controllers/rf59-password.integration.test.ts` cubre CP63 con
SQLite, las migraciones y los triggers reales: hash bcrypt, vigencia exacta,
JWT revocados, permisos y rol efectivo, identidad de confianza, cambio
obligatorio, caducidad ausente o inválida, claves rechazadas, restablecimientos
con la misma fecha y rollback ante fallos de expiración, revocación o auditoría.

`tests/renderer/rf59-ui.mjs` ejecuta la aplicación React con Chromium y conecta
el puente de pruebas con los servicios Main y SQLite. Verifica cancelación,
errores y reintentos, bloqueo de solicitudes duplicadas, visualización única,
rechazo de la contraseña anterior, heartbeat de revocación, redirección a V02,
validación de confirmación y complejidad, cambio definitivo y nuevo login. El
dashboard y el listado usan respuestas de prueba; los servicios de contraseñas,
login, permisos, sesiones y auditoría son los reales.

Se actualiza además la prueba de recuperación de ventas CU43 para comprobar
el nuevo login posterior al cambio obligatorio.

Comandos desde la raíz del proyecto, sin modificar archivos de entorno:

```sh
DATABASE_URL=file:/tmp/huascar-rf59-bootstrap.db npm test
npm run typecheck
npm run build
DATABASE_URL=file:/tmp/huascar-rf59-ui-bootstrap.db node --import tsx tests/renderer/rf59-ui.mjs
node tests/renderer/cu43-ui.mjs
```

La variable de cada comando evita que la conexión global de arranque intente
acceder a Turso. Los casos crean y eliminan su propia base SQLite temporal.
Las pruebas de interfaz requieren Chromium de Playwright y permiso para abrir
un servidor local. `PLAYWRIGHT_CHROMIUM_EXECUTABLE` permite usar una instalación
disponible de Chromium cuando corresponda.
